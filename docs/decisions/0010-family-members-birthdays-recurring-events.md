# ADR 0010 — Family members beyond Immich, birthdays as recurring events, additive migrations

**Status:** proposed  
**Date:** 2026-11-11  
**Extends:** [ADR 0008](0008-family-hub-storage.md). **Supersedes** its "Schema changes" section for `family.db` and `events.db` only.

## Context

Owner requests (2026-11-11):

1. Family settings must let you **add people who aren't Immich users** (a grandmother, a baby),
   and mark which members are Immich users.
2. Every member can have a **birthday**, which appears **automatically in the events list**.
3. Events can be **recurring** (every week / month / year, with an end date).
4. Events can link an **Immich album** (already specified: T-026).

ADR 0008 says "no migrations: on a schema change the old file is kept as `.bak` and the feature
starts empty". That was fine while `family.db` and `events.db` were new. Now they hold what the
family typed in (names, photos, events); starting empty on every added column would be a
regression.

## Decision

### Members

- `family.db` keeps one row per **member**. A member is either an Immich user (`id` = Immich
  user id) or a **manual member** (`id` = a UUID generated by the server, `manual = 1`). The
  server doesn't know which Immich users exist; the app merges the Immich user list with the rows.
- Manual members have no Immich account: they never post on the wall, and they can't be given
  access to an Immich album. They can have a name, a photo (uploaded from the phone, not
  from Immich people) and a birth date. Anyone in the family can add, edit and delete them.
- The app marks Immich users with a badge in Family settings.

### Birthdays are real recurring events

- A birth date (`YYYY-MM-DD`, or `--MM-DD` when the year is unknown) is stored on the member.
  Setting, changing or clearing it makes the server **create, update or delete one event**
  linked to the member (`events.member_id`, `kind = 'birthday'`), repeating yearly.
- The event list needs no special case for birthdays: they are events. Because the event row
  stores the member id and not a copy of the name, a rename never leaves a stale title; the app
  renders "Ola's birthday" from the member and shows the age ("turns 9") when the year is known.
- A birthday event's date, title and repeat can't be edited in Events (`409`): edit the birth
  date in Family settings. Its time, location, note and album can be edited. It can't be deleted
  from Events either; clear the birth date or delete the member.

### Recurring events

- `repeat`: `null` | `weekly` | `monthly` | `yearly`, every 1 period, optional `repeat_until`
  date (inclusive). No other intervals and no RRULE; no per-occurrence exceptions (editing
  changes the whole series). Both are v2 candidates.
- Monthly on the 29th–31st and yearly on 29 February use the month's last day when the date
  doesn't exist. A multi-day event keeps its length in every occurrence.
- The list endpoints return **one entry per series**: the occurrence that is ongoing or next
  (`occurrence_start` / `occurrence_end`). A series is "past" only after its `repeat_until`
  (or never, without one); then it is listed with its last occurrence.

### Additive migrations (supersedes ADR 0008 for these two databases)

- `family.db` and `events.db` may gain **nullable columns** with `ALTER TABLE ... ADD COLUMN`,
  guarded by `PRAGMA user_version`, with no data loss. The version is bumped and the release notes
  say so.
- Anything that can't be done additively (renamed or retyped columns, new constraints) still
  follows ADR 0008: keep the old file as `.v<old>.bak` and start empty.
- Before a migration the store copies the file to `<name>.v<old>.bak` (replacing an older copy),
  so a bug costs a restore, not the data.
- `shopping.db`, `school.db` and `wall.db` are unchanged by this ADR.

## Consequences

- One recurrence implementation serves birthdays, anniversaries and weekly activities.
- The server has to keep the birthday event in step with the member (create, rename, delete);
  tested in T-036.
- A deleted member takes its birthday event with it; an Immich user whose profile row is cleared
  loses the event too.
- The response keeps `start_date` / `end_date` as the series' first occurrence and adds the
  occurrence fields. An app without T-037 shows a recurring event under its first date (it can
  land in the wrong list), so the server and T-037 are released together.
